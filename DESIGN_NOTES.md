FacetOS Design Notes
====================

These are architectural/design notes, not a finalized specification.

Some details are deliberately unresolved. Where this is the case they are
marked as such rather than silently implying that a decision has already
been made.


CORE DESIGN
===========

Basic philosophy:

    POSIXy unless stated otherwise.

FacetOS should provide a familiar POSIX-like environment by default while
also exposing a native object/interface model for functionality that does
not fit naturally into traditional UNIX abstractions.

The system currently runs on seL4 and is heavily divided into isolated
processes, services and domains.

Raw seL4 concepts should generally be hidden behind FacetOS abstractions.
The bootstrap, resource-management and low-level platform layers will
necessarily know about seL4, but higher-level FacetOS code should avoid
depending directly on it where practical.

This is partly to keep the architecture clean and partly to leave open the
possibility of using a different underlying microkernel in the future.


IMPORTANT SECURITY / AUTHORITY PRINCIPLE
========================================

Capabilities determine authority.

Names, configuration settings, domain IDs and claims about being a domain
manager do NOT determine authority.

A process can call itself anything it wants.

A process can run dominit0 itself.

A process can declare itself "Domain 0".

A process can construct an entire nested FacetOS domain hierarchy and call
the root of that hierarchy "Domain 0".

None of these actions grant it any additional authority.

A process/domain can only operate on resources for which it possesses the
necessary capabilities, or which some service possessing the necessary
authority agrees to manipulate on its behalf.

Therefore:

    configuration describes intended behaviour;

    capabilities determine actual authority.

This distinction is fundamental throughout FacetOS.


OBJECTS AND INTERFACES
======================

FacetOS uses an object/interface model inspired primarily by COM and UEFI.

Objects, microkernel servers, devices, special files and other system
resources can expose one or more interfaces.

An interface CONTRACT is identified by a UUID.

An object can be queried using an interface UUID to obtain an INSTANCE of
that interface.

Conceptually:

    Object
      |
      +-- QueryInterface(IID_FOO) --> IFoo instance
      |
      +-- QueryInterface(IID_BAR) --> IBar instance
      |
      +-- QueryInterface(IID_BAZ) --> unsupported / NULL


Local interfaces
----------------

Within the same VSpace/address space, an interface instance is represented
directly as a C structure.

The basic convention is:

    struct IFoo {
        void *self;

        result_t (*method1)(void *self, ...);
        result_t (*method2)(void *self, ...);
        ...
    };

The first member is always:

    void *self

Everything behind self is private to the implementation.

For example, self might point to:

    - a driver structure
    - a filesystem object
    - an seL4-backed kernel object
    - some completely synthetic FacetOS object
    - an IPC proxy

The caller does not need to know.

A local call therefore looks roughly like:

    foo->method1(foo->self, ...);

This should be extremely cheap. Once QueryInterface() has succeeded, normal
method calls are essentially indirect C function calls.


Remote interfaces
-----------------

The same interface model is used when the implementation lives in another
VSpace/process/domain.

In that case an autogenerated interface instance can contain:

    self            -> IPC proxy/private proxy state
    method pointers -> autogenerated IPC client stubs

The caller still uses:

    foo->method1(foo->self, ...);

but the implementation of method1 marshals the arguments, performs the
required microkernel IPC, receives the result, and returns it.

The server side can likewise use autogenerated dispatch code to translate
the IPC request into a call against the real implementation.

Therefore:

    same VSpace:
        interface call -> direct function call

    different VSpace:
        interface call -> generated proxy -> IPC -> server

The source-level interface presented to callers should be the same in both
cases.

Callers should generally not need to know whether an interface is local or
remote.


Microkernel servers
-------------------

FacetOS microkernel servers use the SAME object/interface system.

A process manager, domain manager, filesystem server, device driver, etc.
should not require a separate bespoke programming model simply because it
happens to be implemented as an isolated server.

For example:

    IDomainManager

could be implemented:

    - directly inside the current VSpace using normal function pointers

or:

    - by a parent domain, with the local IDomainManager instance being an
      IPC proxy

The caller should not need to care which is true.


Kernel objects
--------------

Objects backed by underlying microkernel objects can also be represented
through the FacetOS interface model.

The private implementation referenced by self can contain whatever seL4
state is required, including seL4_CPtr values and bookkeeping information.

Higher layers therefore do not necessarily need to manipulate raw seL4
capabilities directly.

seL4 capabilities remain the underlying authority mechanism.

FacetOS interfaces are the programming model presented above that
mechanism.


IDL / code generation
---------------------

Eventually an IDL/code-generation tool should define interfaces and
generate things such as:

    - interface UUID constants
    - C interface structures
    - method declarations
    - local convenience code
    - IPC client proxies
    - IPC server dispatchers
    - possibly generic introspection/invocation metadata

The exact IDL format is NOT YET FINALIZED.


OBJECT STORES
=============

FacetOS has object stores in addition to traditional filesystems.

There is deliberately no single mandatory global registry containing every
object in the system.

Object stores can be stored on block devices.

Mounted object stores can appear in the VFS under something like:

    /objects/StoreUUID/ObjectUUID

The StoreUUID identifies the object store.

The ObjectUUID identifies an object within that store.

An object can expose multiple interfaces.


Filesystem views of object stores
---------------------------------

Adapters can present an object store through a traditional filesystem view.

For example, a filesystem view could expose every object supporting:

    IImage

as files in a directory.

This allows traditional POSIX applications to interact with FacetOS objects
without understanding the native object model.


Object views of filesystems
---------------------------

The reverse should also be possible.

An adapter could present an ordinary filesystem as an object store.

For example, something analogous to the UNIX file(1) mechanism could inspect
files and select suitable interfaces/object types for them.

Files whose type cannot be usefully identified could simply be represented
through a generic interface such as:

    IByteStream

Other interfaces might include:

    ITextFile
    ITextStream
    IImage

etc.

The exact semantics of these interfaces, including things such as text
encoding, remain to be designed.


Adapters
--------

Adapters allow the same underlying information/resource to be exposed
through different views.

Important details such as adapter identity, mutability, persistence and
whether an adapted object is merely a view or a separately persistent
object are NOT YET FINALIZED.


POSIX INTEGRATION
=================

The native FacetOS object model can be exported into:

    - a POSIX view
    - a pure POSIX domain

so that traditional UNIX applications can interact with FacetOS resources.

The intent is not to replace POSIX unnecessarily.

Native interfaces exist where they are useful; ordinary software should
still be able to live in a recognizable UNIX-like environment.


DOMAINS
=======

A FacetOS domain is primarily a userspace organizational, resource and
security abstraction built on top of the underlying capability system.

A domain is NOT simply:

    - one process
    - one thread
    - one VSpace
    - necessarily an environment running FacetOS software

A domain represents a collection of resources and authority delegated from
a parent domain.

A domain may contain:

    - native FacetOS processes and services
    - POSIX personality processes
    - drivers
    - child domains
    - virtual machines running other operating systems
    - combinations of the above

Normally a native FacetOS domain has a dominit0 instance responsible for
initializing and managing it.

However, dominit0 is NOT what makes something a domain.

For example, a domain whose workload is an OpenBSD VM may contain no
FacetOS userspace beyond whatever external FacetOS machinery is required
to provide and manage its resources.

Conceptually:

    FacetOS Domain
        |
        +-- delegated RAM
        +-- delegated CPUs / scheduling resources
        +-- delegated or virtual devices
        +-- delegated services
        +-- capability authority
        |
        +-- workload:
                OpenBSD VM

The OpenBSD system is therefore not merely "a VM running inside a domain"
in the architectural sense.

The VM itself represents the workload/personality of that domain.


Domain types / personalities
----------------------------

Domains can have different intended personalities.

Current examples include:

    - pure FacetOS domain
    - pure POSIX domain
    - virtual-machine domain running another operating system

The distinction describes what environment the domain presents internally,
not a fundamentally different resource/security model.

For example:

    FacetOS domain
        |
        +-- dominit0
        +-- native FacetOS processes

    Pure POSIX domain
        |
        +-- POSIX init / PID 1
        +-- POSIX processes

    OpenBSD VM domain
        |
        +-- VMM
        +-- OpenBSD kernel
        +-- OpenBSD userspace

All three are domains from the perspective of the parent.

The parent delegates resources and authority to each and need not treat
the VM as architecturally outside the domain model.


Virtual-machine domains
-----------------------

A domain may use its delegated resources to run an entirely different
operating system under a VMM.

Examples might include:

    - OpenBSD
    - Linux
    - another FacetOS instance
    - some other operating system

The VMM and whatever FacetOS components support it are implementation
details of the domain.

From the parent's perspective, the important facts remain:

    - which resources belong to the domain
    - which capabilities/authority were delegated to it
    - which interfaces/services it exposes
    - which interfaces/services from the parent it may access

A VM domain can therefore participate in the wider FacetOS system through
adapters and conventional protocols.

For example, an OpenBSD VM domain could provide networking services to
other domains.

A Linux VM domain could own the physical GPU and provide Wayland/X11 or
other graphics services.

The fact that the service implementation happens to live inside another
operating system does not make it fundamentally different from another
isolated FacetOS service.


Nested virtualization and domains
---------------------------------

The recursive domain model applies equally to virtual machines.

For example:

    Domain 0
        |
        +-- Domain 1
        |     pure FacetOS
        |
        +-- Domain 2
        |     OpenBSD VM
        |
        +-- Domain 3
              Linux VM
              |
              +-- QEMU
                    |
                    +-- nested guest

The nested guest can itself be treated as another domain hierarchy if the
software managing it chooses to expose it that way.

Likewise, another complete FacetOS instance running inside a VM can call
its own root:

    Domain 0

without conflicting with the outer Domain 0.

Again, domain hierarchy and naming do not manufacture authority.
Everything remains constrained by the resources/capabilities ultimately
delegated from outside.


Pure POSIX domain
-----------------

A pure POSIX domain is a FacetOS domain whose primary personality is POSIX.

Conceptually it has its own domain-level UNIX environment, including:

    - its own /etc
    - its own process environment / namespace
    - a POSIX process running as PID 1
    - /sbin/init or equivalent
    - getty/login etc. if desired

Unlike a VM domain, the POSIX personality can be implemented directly on
FacetOS rather than by running a separate guest kernel.

This gives an important distinction:

    POSIX view:
        POSIX compatibility presented inside an existing FacetOS domain.

    Pure POSIX domain:
        separate domain running the FacetOS POSIX personality.

    UNIX VM domain:
        separate domain whose workload is an actual UNIX kernel and its
        userspace.


VIRTUAL CONSOLES
================

One possible setup:

    Alt-F1:
        Domain 0
        Pure FacetOS login/shell

    Alt-F2:
        POSIX view of Domain 0

    Alt-F3:
        Pure POSIX domain
        FacetOS POSIX personality
        Own /sbin/init as PID 1
        getty/login etc.

    Alt-F4:
        OpenBSD VM domain
        Possibly providing networking services

    Alt-F5:
        Linux VM domain
        Possibly owning the GPU and providing Wayland/X11 services

This is an example of what the domain architecture should make possible,
not a mandatory fixed console layout.


DOMINIT0
========

dominit0 is the program normally responsible for bootstrapping and managing
a native FacetOS domain.

Not every FacetOS domain necessarily runs dominit0 as its internal workload.
For example, a VM domain may instead be constructed by its parent and begin
execution directly in a VMM/guest environment.

"Domain" describes the resource/security boundary and delegated authority;
"dominit0" is one mechanism for constructing and managing a FacetOS-native
environment inside that boundary.

The same basic dominit0 design should be usable for:

    - Domain 0, started by the underlying microkernel
    - child domains, started by another dominit0
    - nested/private FacetOS hierarchies started by ordinary processes

This recursive model is intentional.


Configuration model
-------------------

dominit0 has one generic configuration model describing the domain it is
being asked to initialize.

Configuration can originate from three sources:

    1. command-line arguments
    2. a root-domain configuration file
    3. a startup environment supplied by a parent

All three sources should ultimately populate/update the same generic
configuration structures. The parsing and application of configuration
belongs in generic code, initially config.c/config.h, rather than in the
seL4 platform layer.

Conceptually:

    defaults
       |
       v
    DomainConfig
       ^
       |
       +-- command-line parser
       |
       +-- root configuration-file parser
       |
       +-- parent-supplied environment parser

A configuration source need not specify every field. Unspecified fields keep
their defaults or values established by an earlier configuration layer.

The exact precedence rules are not yet finalized, but for Domain 0 a sensible
initial rule is:

    built-in defaults
        -> root configuration file
        -> command-line overrides

For a child, the parent-supplied startup environment is the normal source of
its configuration.


Per-domain configuration
------------------------

The generic per-domain configuration should describe policy and intended
behaviour for one domain.

Initial fields are expected to include things such as:

    - domain ID
    - human-readable domain name
    - domain type/personality
        - native
        - POSIX
        - later VM/other personalities
    - console assignment
        - default console, initially tty1
        - whether to start a console server
        - console/seat name, initially seat0
    - domain-management mode
        - no domain management
        - manage children locally
        - request domain-management operations through a parent-provided
          IDomainManager interface
    - log level for the domain
    - other per-domain startup policy as it becomes necessary

The configuration structure should remain independent of seL4 where practical.
Raw seL4_CPtr values, BootInfo pointers, VKA/VSpace objects and similar
platform details do not belong in the generic DomainConfig.

Configuration describes intended behaviour. It does not grant authority.


Root-domain configuration file
------------------------------

The configuration file is specifically a root-of-hierarchy input.

It describes:

    - the configuration of the root domain itself
    - the child domains the root should construct
    - the configuration to supply to each child
    - hierarchy/parent relationships where necessary
    - per-child policy such as log level, console, personality and
      domain-management mode
    - eventually requested/delegated resources, initial services, drivers,
      programs and other startup policy

Conceptually:

    SystemConfig
        |
        +-- root DomainConfig
        |
        +-- child DomainConfig
        |
        +-- child DomainConfig
        |
        +-- ...

The file is not intended to be the normal mechanism by which an already
running parent configures a child. The parent reads the hierarchy
configuration, selects the relevant DomainConfig for a child, constructs the
child's startup environment, and starts the child with that environment.

A child therefore does not need to parse or possess the root's complete
configuration file.

The exact human-readable file syntax is NOT YET FINALIZED.


Parent-supplied startup environment
-----------------------------------

A parent configures a child by constructing a startup environment for it.

That environment carries two logically distinct categories of information:

    CONFIGURATION

        The child's DomainConfig: what the child is intended to construct,
        run and do.

    DELEGATED ENVIRONMENT / AUTHORITY

        The resources, interfaces and capabilities the parent has actually
        made available to the child.

The representation may initially be human-readable and may share parsing
machinery with command-line configuration. It does not have to remain an
argv-style command line forever.

For example, the parent may tell a child:

    domain.id=2
    domain.name=posix
    domain.type=posix
    log.level=debug
    console.device=tty3
    domain.manager=parent

while separately making the corresponding resources/interfaces available in
the child's startup environment.

The configuration statement:

    domain.manager=parent

means that the child is configured to use domain-management services supplied
by its parent. It does not itself grant access to such a service.

Likewise, a numeric capability reference is meaningful only if the parent has
actually installed the corresponding capability into the child's CSpace.


Domain 0 startup
----------------

Currently the underlying microkernel is seL4.

The initial startup path is approximately:

    bootloader
        |
        v
    seL4
        |
        v
    seL4 root task environment / BootInfo
        |
        v
    dominit0
        |
        v
    Domain 0

Domain 0 obtains two different kinds of startup input:

    CONFIGURATION

        - built-in defaults
        - optional root-domain configuration file/module
        - command-line arguments

    PLATFORM ENVIRONMENT

        - seL4 BootInfo and the resources/capabilities represented by it

The seL4 platform/bootstrap layer should translate BootInfo into the generic
FacetOS environment/resource abstractions needed by dominit0.

Long term, generic configuration code should not depend on seL4_BootInfo.

Conceptually:

    command line ---------+
                          |
    root config file -----+--> config.c --> DomainConfig/SystemConfig
                          |
    defaults -------------+

    seL4 BootInfo
        |
        v
    seL4 bootstrap adapter
        |
        v
    FacetOS delegated/resource environment

These meet in dominit0, but remain conceptually separate.


Child domain startup
--------------------

A child domain is conceptually given a subset of the environment/resources
that its parent possesses.

The parent creates the resources required for the child, including things
such as:

    - child CSpace
    - child VSpace
    - initial TCB/thread
    - memory/resources
    - dominit0 executable mappings
    - child's DomainConfig/startup environment
    - explicitly delegated capabilities/interfaces

The parent does not pass its complete root configuration file to the child.
It constructs the child's effective configuration from the relevant
DomainConfig and supplies that configuration as part of the child's startup
environment.

This means a root configuration can say, for example:

    "start child 3 with debug logging, tty4, POSIX personality and
     parent-proxied domain management"

without requiring child 3 to know anything about the configuration of its
siblings.

The resulting startup environment should deliberately resemble, at a semantic
level, the environment that the underlying microkernel gives to Domain 0.

From the child's point of view:

    "This is my configuration, and these are the resources/authority available
     to my domain."

The child should not need to care whether those resources ultimately came
from physical hardware, its parent, a VM, or another abstraction layer.


Recursive bootstrap
-------------------

The intended recursive model is roughly:

    physical machine
          |
         seL4
          |
          v
       dominit0
       Domain 0
          |
          +-- processes/services
          |
          +-- dominit0
          |   Domain 1
          |       |
          |       +-- processes/services
          |       |
          |       +-- dominit0
          |           Domain 3
          |
          +-- dominit0
              Domain 2

Nothing says that only the officially configured dominit0 processes may do
this. Any process with sufficient resources and authority can construct a
nested hierarchy and configure its children using the same environment model.

The nested hierarchy remains constrained by the resources and capabilities
available to the process constructing it.


Capability references in startup environments
---------------------------------------------

The parent constructs the child's CSpace.

A capability is NOT passed merely by writing its numeric value into
configuration or a startup environment.

Instead:

    1. The parent copies/mints/delegates the capability into a slot in the
       child's CSpace.

    2. The parent describes how the child can find/use that capability in the
       child's startup environment.

During early development this may be represented by human-readable numeric
CPtr values.

For example:

    domain-manager-cap=291

means approximately:

    "The capability you should use for the parent-provided IDomainManager is
     available as CPtr 291 in your CSpace."

The integer itself grants no authority.

The long-term representation of delegated interfaces/resources is NOT YET
FINALIZED and should not be baked unnecessarily into DomainConfig.


Configuration versus authority
------------------------------

Keep these concepts distinct:

    CONFIGURATION

        What this instance of dominit0 is intended to construct/run/do.

        Configuration may come from a command line, the root hierarchy file,
        or a parent-supplied startup environment.

    ENVIRONMENT / DELEGATED AUTHORITY

        What resources, interfaces and capabilities are actually available.

        For Domain 0 this currently originates largely in seL4 BootInfo.

        For child domains the parent constructs it.

        For a nested hierarchy started by an ordinary process, that process
        constructs whatever environment it can from the resources available
        to it.

The fundamental rule remains:

    configuration describes intended behaviour;
    capabilities determine actual authority.


Domain management through a parent
----------------------------------

A domain may be configured to use an IDomainManager interface implemented by
its parent.

For example:

    child
      |
      +-- IDomainManager proxy
              |
              | IPC
              v
           parent dominit0

This allows the child to REQUEST domain-management operations involving
resources controlled by its parent.

The child is not necessarily given raw authority over those resources.
Instead, the parent retains that authority and decides whether to perform the
requested operation.

This is normal FacetOS interface delegation:

    interface presented locally
        |
        v
    generated IPC proxy
        |
        v
    implementation possessing actual authority


INITRD AND DRIVER/SERVICE LOADING
=================================

dominit0 should eventually load required drivers/services from an initrd.

Drivers should normally run isolated rather than simply becoming threads
with unrestricted access to dominit0's VSpace.

The parent/domain resource manager should grant each driver only the
resources/capabilities required for that driver.

Drivers and services should expose their functionality using the normal
FacetOS interface system.

The exact initrd format and driver metadata/configuration format are NOT YET
FINALIZED.


PROCESS MODEL
=============

The domain's process table is expected to be managed by dominit0/root-domain
infrastructure.

Early development can begin with kernel/service threads running inside the
dominit0 VSpace.

Later, proper processes/services should receive:

    - their own VSpace where appropriate
    - restricted CSpaces
    - explicitly delegated capabilities
    - TCBs/threads configured by the domain manager

The distinction between "kernel thread", service and process needs further
design as implementation progresses.


MEMORY / RESOURCE MANAGEMENT
============================

Initial dependency chain:

    bootstrap allocator
        |
        v
    parse bootstrap/BootInfo resources
        |
        v
    CSpace allocator
        |
        v
    Untyped/resource manager
        |
        v
    seL4 kernel-object allocation
        |
        v
    physical Frames
        |
        v
    VSpace management
        |
        v
    real kernel heap / kmalloc
        |
        v
    higher-level objects/processes/services


Bootstrap allocator
-------------------

Use a large static chunk in .bss.

The bootstrap allocator should be deliberately simple:

    - monotonic/bump allocation
    - alignment support
    - bounds checking
    - no meaningful free()

It exists to break allocator bootstrap dependency cycles.

Memory used permanently for early allocator metadata does not necessarily
need to be reclaimed later.


Untyped/resource management
---------------------------

Parse the resources supplied by seL4 BootInfo and record all Untyped
capabilities/resources.

Track at least:

    - capability/slot
    - physical address where available
    - sizeBits
    - device/non-device
    - allocation/retype/provenance state

The resource manager should eventually be able to select suitable Untyped
resources and retype them into required seL4 objects.

Higher layers should not need to understand Untyped allocation directly.


Kernel object allocation
------------------------

Provide a layer that combines:

    - destination CSlot allocation
    - suitable Untyped selection
    - seL4_Untyped_Retype()
    - bookkeeping/provenance
    - cleanup/error handling

The low-level implementation can expose higher-level FacetOS interfaces
rather than leaking raw seL4 capabilities everywhere.


Kernel heap
-----------

Once physical Frames and VSpace management work, implement a real dynamic
kernel heap:

    kmalloc()
    kfree()

The real heap should acquire additional backing memory through the normal
FacetOS resource/frame/VSpace machinery.

Bootstrap allocations can remain permanently allocated.


KLOG
====

Early klog exists / is being developed specifically so that memory
management can be debugged without depending on dynamic allocation.

Early boot:

    - write into static buffer
    - emit to seL4 debug output

Later:

    - add VGA/console output
    - once kmalloc is available, migrate/preserve the early log into larger
      dynamically allocated storage
    - eventually use a proper ring buffer or equivalent
    - support dynamically registered sinks
    - expose retained log through a dmesg-like interface

The important invariant is:

    Logging required to debug the allocator must not itself require the
    allocator to work.


BOOTSTUB32
==========

SIDE PROJECT / NOT CURRENTLY ON THE FACETOS CRITICAL PATH.

Investigate a small 32-bit boot stub that can load a Multiboot2 kernel and
modules in a form that allows QEMU's:

    -kernel

mechanism to work conveniently.

This might also be useful as a standalone/upstream tool for other projects.

Do not accidentally spend three days writing this instead of the FacetOS
memory manager.
